# MIT 6.5840 Lab 3(Raft) Part B：Log Replication

------

## 1. Lab 3B 简介

在 3A 中，已经完成了 **leader election**，让集群能够在没有 leader 时选出一个新的 leader，并且通过 heartbeat 维持身份。

但仅仅选出 leader 还远远不够。Raft 真正要解决的问题不是“谁是 leader”，而是“**多个副本如何对同一串操作达成一致**”。这便是 3B 的目标：实现 **log replication**。

从这一部分开始，leader 不再只是周期性发空的 `AppendEntries` 维持身份，而是要真正把客户端提交的命令追加到自己的日志中，再复制给其他节点，最后在合适的时候把这些日志提交并应用到状态机。

简而言之，3A 解决“集群里谁说了算”，3B 要是实现“说了算的人，如何让大家做同一件事”。

## 2. Lab 3B 任务描述

实验说明对 Part 3B 的要求大致可以概括为：

- 实现 `Start()`，用于处理客户端新发送的命令，注意只有 leader 才有资格接收客户端命令；
- 完成 `AppendEntries RPC` 的真正逻辑，不只是3A的 heartbeat；
- leader 要能够把新日志复制给 follower；
- follower 要能够检查日志一致性，并在必要时删除冲突日志（第一个和 leader 冲突及其之后的所有日志）；
- leader 在选举成功和复制日志成功时要更新 `nextIndex[]` 和 `matchIndex[]`；
- 当某条日志被半数以上的节点复制后，leader 应该推进 `commitIndex`；
- 所有节点都要在日志提交后，通过 `applyCh` 把日志发送给上层状态机。

我们滤清一下论文 Figure 2 的关键链路：

1. 客户端命令先进入 leader 本地日志（对应 `Start()`）；
2. leader 把日志发给 followers（在 `AppendEntries` 中添加逻辑）；
3. followers 校验并写入日志；
4. leader 每次心跳后统计日志复制情况，确认是否达到多数（对应 `updateCommitIndex()`）；
5. 达到多数后推进提交（使用 `applyEntries()`）；
6. 每个节点把已经提交的日志 apply 到状态机（使用 `applyEntries()`）。

## 3. 整体思路

3B 的实现本质上是围绕一条主线展开的：

**客户端命令先写 leader 本地日志，再由 leader 负责把日志复制到多数节点，最后宣布提交。**

### 3.1 leader 追加本地日志

服务层调用 `Start(command)` 后，如果当前节点不是 leader，就直接返回；如果是 leader，就把这条命令追加到自己的 `log` 里，并立刻返回给上层。

注意：`Start()` **只负责开始 agreement，不负责等待提交完成**。这一点实验文档也明确要求了。

### 3.2 leader 向 followers 同步日志

leader 周期性调用 `sendHeartbeat()`， 3B 里这个函数不再只是发空心跳。它会根据每个 follower 在 leader 对应的 `nextIndex[server]`，决定应该从 leader 的哪一条日志开始同步。

如果 follower 的日志能和 `AppendEntries` 的参数匹配上，那么这次 `AppendEntries` 就会成功，RPC 返回后 leader 就更新对应 follower 的 `nextIndex[]` 和 `matchIndex[]`。

如果失败，说明 follower 的日志和 leader 在某个位置不一致，leader 就把 `nextIndex[]` 往前退一格，下次继续重试。

### 3.3 follower 检查并修复日志

follower 收到 `AppendEntries` 后，会按论文 Figure 2 的规则做以下几件事：

1. 检查 term 是否过期；
2. 检查 `PrevLogIndex` 和 `PrevLogTerm` 是否能对上；
3. 如果发现冲突日志，就删除冲突位置以及之后的所有日志；
4. 把 leader 发来的新日志追加进来；
5. 根据 `LeaderCommit` 判断是否更新自己的 `commitIndex`。

### 3.4 leader 推进提交并 apply

日志复制成功并不等于日志提交成功。
leader 还要检查：是否存在某个日志下标 `N`，使得大多数节点的 `matchIndex[i] >= N`，并且 `log[N].Term == currentTerm`。如果满足，leader 才能把 `commitIndex` 推进到 `N`。

推进提交后，再调用 `applyEntries()`，把所有新提交但尚未 apply 的日志，按顺序通过 `applyCh` 发送给上层。

## 4. 代码实现拆解

### 4.1 日志结构与初始化

在 3B 中，日志开始发挥作用。

日志项定义如下：

```go
type LogEntry struct {
	Command any
	Term    int
}
```

`Command` 表示状态机命令，`Term` 表示这条日志是在哪个任期被 leader 接收的。

在 `Make()` 中，用一个 dummy entry 作为初始日志（`Make()` 的完整代码见 3A 文章）：

```go
rf.log = []LogEntry{{Term: 0}}
```

这样可以把日志当成“逻辑上从 1 开始编号，但代码从 0 开始访问”。这样 `PrevLogIndex = 0` 的情况就合法了，简化了很多边界条件的处理。

同时，关键的还有 leader 的两个数组：

```go
rf.nextIndex = make([]int, len(peers))
rf.matchIndex = make([]int, len(peers))
```

它们的语义是：

- `nextIndex[i]`：下次要发给 follower `i` 的第一条日志下标
- `matchIndex[i]`：目前已知 follower `i` 已经复制成功的最高日志下标

### 4.2 Start()

`Start()` 是客户端命令进入 Raft 的入口。

```go
func (rf *Raft) Start(command any) (int, int, bool) {
	rf.mu.Lock()
	defer rf.mu.Unlock()

	isLeader := rf.role == LEADER
	if !isLeader {
		return -1, rf.currentTerm, isLeader
	}

	index := len(rf.log)
	term := rf.currentTerm

	rf.log = append(rf.log, LogEntry{
		Command: command,
		Term:    term,
	})

	return index, term, isLeader
}
```

这部分逻辑比较简单：

- 先判断自己是不是 leader；
- 如果不是，直接返回；
- 如果是，就把命令追加到本地日志末尾；
- 返回这条日志未来的 `index`、当前 `term` 和 `isLeader`。

注意：

#### Leader 先写本地，再复制给别人

Raft 的日志流向始终是 **leader -> follower**。因此客户端命令一定是先进入 leader 的日志，再由 leader 负责把它同步出去，原则上系统中客户端只会和 leader 直接通信。

### 4.3 leader 当选后更新 `nextIndex[]` 和 `matchIndex[]`

在 `startElection()` 中，增加 candidate 获得多数票并当选 leader 后的逻辑：

```go
if reply.VoteGranted {
	newVotes := atomic.AddInt32(&votes, 1)
	if int(newVotes) > len(rf.peers)/2 {
		rf.role = LEADER
		rf.lastHeartbeat = time.Now()

        // ====新增逻辑====
		lastIndex := len(rf.log)
		for i := range rf.peers {
			rf.nextIndex[i] = lastIndex
			rf.matchIndex[i] = 0
		}
        // ===============

		go rf.leaderLoop()
		go rf.sendHeartbeat()
	}
}
```

这里的含义是：

- `nextIndex[i] = leader最后一条日志下标 + 1`
- 切片长度其实就是下一条可写位置，所以直接设成 `len(rf.log)` 即可；
- `matchIndex[i] = 0`，表示一开始还只知道大家至少匹配到了 dummy entry。

这一步对应论文 Figure 2 里的：

> Volatile state on leaders:
> `nextIndex[]` initialized to leader last log index + 1
> `matchIndex[]` initialized to 0

### 4.4 sendHeartbeat()

到了 3B，`sendHeartbeat()` 的名字虽然没变，但它做的事情已经从“发空包维持 leader 身份”，变成了“按需发送日志复制请求”。

```go
func (rf *Raft) sendHeartbeat() {
	for i := range rf.peers {
		if i == rf.me {
			continue
		}

		go func(server int) {
			rf.mu.Lock()
			term := rf.currentTerm
			prevLogIndex := rf.nextIndex[server] - 1
			prevLogTerm := rf.log[prevLogIndex].Term
			entries := rf.log[rf.nextIndex[server]:]
			args := AppendEntriesArgs{
				Term:         term,
				LeaderId:     rf.me,
				PrevLogIndex: prevLogIndex,
				PrevLogTerm:  prevLogTerm,
				Entries:      entries,
				LeaderCommit: rf.commitIndex,
			}
			rf.mu.Unlock()

			reply := AppendEntriesReply{}
			rf.sendAppendEntries(server, &args, &reply)

			rf.mu.Lock()
			defer rf.mu.Unlock()

			if rf.role != LEADER || term != rf.currentTerm {
				return
			}

			if reply.Success {
				rf.nextIndex[server] = args.PrevLogIndex + len(args.Entries) + 1
				rf.matchIndex[server] = rf.nextIndex[server] - 1
			} else {
				if reply.Term == rf.currentTerm {
					rf.nextIndex[server] = max(1, rf.nextIndex[server]-1)
				}
			}

			if reply.Term > rf.currentTerm {
				rf.currentTerm = reply.Term
				rf.role = FOLLOWER
				rf.votedFor = -1
				rf.lastHeartbeat = time.Now()
			}
		}(i)
	}
}
```

这段代码可以拆成三层理解。

#### 第一层：根据 `nextIndex[]` 决定发什么

对每个 follower 收到的 `AppendEntries`：

- `prevLogIndex := rf.nextIndex[server] - 1`
- `prevLogTerm := rf.log[prevLogIndex].Term`
- `entries := rf.log[rf.nextIndex[server]:]`

含义是：我认为你已经匹配到了 `prevLogIndex`，那我现在把从 `nextIndex` 开始的所有日志发给你

如果 follower 的日志确实和 leader 能够匹配，就能成功追加。

#### 第二层：复制成功后推进匹配位置

如果 `reply.Success == true`，说明 follower 的日志已经和 leader 对齐到了新位置，这时就更新：

```go
rf.nextIndex[server] = args.PrevLogIndex + len(args.Entries) + 1
rf.matchIndex[server] = rf.nextIndex[server] - 1
```

含义是：follower 已经匹配到更后面了，下次从第一个未匹配的位置开始发即可

#### 第三层：失败就回退 `nextIndex[]`

如果失败，并且不是因为 term 变大，而是单纯日志不一致，那么我这里采取了最朴素的处理方式：

```go
rf.nextIndex[server] = max(1, rf.nextIndex[server]-1)
```

也就是 **每次退一格**，只要不断往前试，总能找到 leader 和 follower 最后一个共同前缀的位置。因为设置了 dummy entry ，所以 `nextIndex` 的最小值是1

### 4.5 AppendEntries RPC

follower 侧的核心，相比 3A 多了很多逻辑：

```go
// AppendEntries RPC handler.
func (rf *Raft) AppendEntries(args *AppendEntriesArgs, reply *AppendEntriesReply) {
	rf.mu.Lock()
	defer rf.mu.Unlock()
	reply.Success = false
	reply.Term = rf.currentTerm

	rf.lastHeartbeat = time.Now() // 更新上次收到心跳的时间
	// 当 follower 和 candidate 收到任期号比自己大的 AppendEntries RPC 时，说明自己过时了，转变为 FOLLOWER
	if args.Term > rf.currentTerm {
		rf.currentTerm = args.Term
		rf.votedFor = -1
		rf.role = FOLLOWER
	}

	// candidate 收到 AppendEntries(term >= currentTerm) 会立即转 follower
	if args.Term == rf.currentTerm && rf.role == CANDIDATE {
		rf.role = FOLLOWER
		rf.votedFor = -1
	}

	// Reply false if term < currentTerm
	if args.Term < rf.currentTerm {
		return
	}

	// Reply false if log doesn’t contain an entry at prevLogIndex whose term matches prevLogTerm
	// 在日志中没有包含一个索引为 prevLogIndex 且任期号为 prevLogTerm 的条目时，回复 false
	if args.PrevLogIndex >= len(rf.log) { // prevLogIndex 可能超过了当前日志的长度
		return
	}

	if args.PrevLogIndex >= 0 && args.PrevLogIndex < len(rf.log) && rf.log[args.PrevLogIndex].Term != args.PrevLogTerm {
		return
	}

	// If an existing entry conflicts with a new one (same index but different terms), delete the existing entry and all that follow it
	// 当一个已经存在的条目和一个新的条目发生冲突（索引相同但任期号不同）时，删除已经存在的条目和它之后的所有条目
	offset := 0
	for i, entry := range args.Entries {
		index := args.PrevLogIndex + 1 + i
		if index < len(rf.log) {
			// 找到第一个冲突的条目，删除它和之后的所有条目
			if rf.log[index].Term != entry.Term {
				rf.log = rf.log[:index]
				break
			}
			offset = i + 1
		} else {
			break
		}
	}

	// Append any new entries not already in the log
	// 将所有新的条目追加到日志中
	for i := offset; i < len(args.Entries); i++ {
		rf.log = append(rf.log, args.Entries[i])
	}

	// If leaderCommit > commitIndex, set commitIndex = min(leaderCommit, index of last new entry)
	// 当 leaderCommit 大于 commitIndex 时，将 commitIndex 更新为 leaderCommit 和最后一个新条目的索引中的较小值
	if args.LeaderCommit > rf.commitIndex {
		lastIndex := len(rf.log) - 1
		rf.commitIndex = min(args.LeaderCommit, lastIndex)
		rf.applyEntries() // 应用已提交的日志条目
	}

	reply.Success = true
	reply.Term = rf.currentTerm
}
```

#### 检查 1：`PrevLogIndex` 不能越界

如果 leader 认为 follower 至少应该有 `PrevLogIndex` 这一项，但 follower 自己的日志长度都不够，那显然不匹配，直接返回 `false`。

#### 检查 2：`PrevLogTerm` 必须一致

即便 `PrevLogIndex` 存在，也还要检查这一项的 term 是否和 leader 提供的一致。
如果不同，说明双方日志在这个位置已经分叉了，也必须返回 `false`。

这两步共同对应论文 Figure 2 里的：

> Reply false if log doesn’t contain an entry at prevLogIndex whose term matches prevLogTerm

即 **leader 只能在一个双方都承认的共同前缀之后追加新日志**。

### 4.5.1 冲突日志删除与新日志追加

分析一下删除冲突日志和追加日志的部分。在通过一致性检查后，就要真正处理日志了。

```go
offset := 0
for i, entry := range args.Entries {
	index := args.PrevLogIndex + 1 + i
	if index < len(rf.log) {
		if rf.log[index].Term != entry.Term {
			rf.log = rf.log[:index]
			break
		}
		offset = i + 1
	} else {
		break
	}
}
rf.log = append(rf.log, args.Entries[offset:]...)
```

#### 第一步：找第一个冲突点

如果某个位置：

- index 相同
- 但 term 不同

那就说明 follower 在这个位置及之后的日志，已经不可信了。按照论文要求，要把这个位置以及后面的日志全部删掉：

```go
rf.log = rf.log[:index]
```

#### 第二步：追加 leader 发来的新日志

删完之后，从第一个还没匹配上的位置开始，把 leader 的日志补进来。

这一步体现的是 Raft 一个非常强的约束：

> follower 的日志最终必须变成 leader 日志的前缀扩展

### 4.7 commitIndex 的推进与 follower apply

follower 收到 `AppendEntries` 后，除了写日志，还要处理 leader 通知下来的提交进度：

```go
if args.LeaderCommit > rf.commitIndex {
	lastIndex := len(rf.log) - 1
	rf.commitIndex = min(args.LeaderCommit, lastIndex)
	rf.applyEntries()
}
```

- 如果 leader 已经提交到了更靠后的位置；
- follower 就把自己的 `commitIndex` 推进到 `min(leaderCommit, lastIndex)`；
- 不能盲目设成 `leaderCommit`，因为 follower 自己可能还没收到那么多日志。

推进后调用 `applyEntries()`：

```go
func (rf *Raft) applyEntries() {
	for rf.lastApplied < rf.commitIndex {
		rf.lastApplied++
		rf.applyCh <- raftapi.ApplyMsg{
			CommandValid: true,
			Command:      rf.log[rf.lastApplied].Command,
			CommandIndex: rf.lastApplied,
		}
	}
}
```

这个函数把所有“已提交但尚未执行”的日志，按顺序应用到状态机。

### 4.8 updateCommitIndex()

日志复制到 follower，不代表已经提交；
复制到一部分 follower，也不代表已经提交；
**只有复制到多数节点，leader 才能宣布提交。**

对应实现就是 `updateCommitIndex()`：

```go
func (rf *Raft) updateCommitIndex() {
	rf.mu.Lock()
	defer rf.mu.Unlock()
	// If there exists an N such that N > commitIndex, a majority of matchIndex[i] ≥ N, and log[N].term == currentTerm: set commitIndex = N
	// 找到满足条件的最大的 N，将 commitIndex 更新为 N
	for N := len(rf.log) - 1; N > rf.commitIndex; N-- {
		if rf.log[N].Term != rf.currentTerm {
			continue
		}
		count := 1 // 包括 leader 自己
		for i := range rf.peers {
			if i != rf.me && rf.matchIndex[i] >= N {
				count++
			}
		}
		if count > len(rf.peers)/2 {
			rf.commitIndex = N
			rf.applyEntries() // 提交新的日志条目
			break
		}
	}
}
```

#### 只提交当前 term 的日志

注意这段代码：

```go
if rf.log[N].Term != rf.currentTerm {
	continue
}
```

这是论文 5.4.2 里说到的：
**leader 不能仅靠“多数副本”就直接提交旧任期的日志。**

Raft 更保守的规则是：

- 只有当前任期的日志，可以通过“多数副本”直接提交；
- 一旦当前任期某条日志提交了，那么它前面的所有日志也会被视为已提交。

### 4.9 leaderLoop()

将更新 commitIndex 添加到了循环的末尾：

```go
func (rf *Raft) leaderLoop() {
	for rf.killed() == false {
		time.Sleep(HEARTBEAT_INTERVAL)
		rf.mu.Lock()
		if rf.role != LEADER {
			rf.mu.Unlock()
			return
		}
		rf.mu.Unlock()
		rf.sendHeartbeat()
		rf.updateCommitIndex() // 新增
	}
}
```

它周期性做两件事：

1. 调用 `sendHeartbeat()`，同步日志或发送 heartbeat；
2. 调用 `updateCommitIndex()`，尝试推进提交位置。

也就是说在3A中，leader 的生命周期已经从“维持 authority”扩展成了“维持 authority + 日志复制 + 提交到状态机”。

## 5. 容易踩坑的点

### 5.1 `nextIndex[]` 初始化一定要是“最后日志下标 + 1”

不是最后日志下标本身，而是再加一。

`nextIndex[i]` 表示的是：

> 下一次要发给该 follower 的第一条日志位置

所以如果 leader 当前最后一条日志下标是 `lastLogIndex`，那初始化时就该是 `lastLogIndex + 1`。
由于日志下标是从0开始的，所以直接用 `len(rf.log)` 即可。

------

### 5.2 复制成功不等于提交成功

某个 follower 成功接收了 leader 的日志，只说明“这个 follower 和 leader 对齐到了更靠后的位置”；
只有当 **大多数节点** 都完成了复制，leader 才能更新 `commitIndex`。

因此：

- `AppendEntries` 成功是“复制层面”的概念；
- `commitIndex` 推进是“共识层面”的概念。

两者不能混为一谈。

------

### 5.3 只能用当前 term 的日志推进提交

这是 3B 里很容易漏掉，但又非常关键的一条规则。

如果不加：

```go
if rf.log[N].Term != rf.currentTerm {
	continue
}
```

在某些 leader 切换场景下，就可能错误地把旧任期的日志判定为已提交，从而破坏 Raft 的安全性。

也就是说，**“多数复制”还不够，必须是“当前任期的多数复制”**。
前面旧任期的日志，得等当前任期某条日志真正提交以后，才能被一并“带着提交”。

------

### 5.4 处理 RPC 回复时，一定要重新检查 role 和 term

在 `sendHeartbeat()` 里：

```go
if rf.role != LEADER || term != rf.currentTerm {
	return
}
```

这是因为 RPC 回复可能会延迟、乱序甚至过期。

你发送请求时是 leader，不代表收到回复时还是 leader；
你发送请求时 term 是 `T`，不代表收到回复时自己还停留在 `T`。

如果不重新检查，就可能让旧消息污染当前状态，导致 `nextIndex[]`、`matchIndex[]` 甚至角色切换都出问题。

3B 做完之后，它才真正开始变成一个“**能复制日志的共识系统**”。

这一部分我最大的感受是，Raft 真正巧妙的地方，不是它用了什么很花哨的技巧，而是它把整个问题拆得很清楚：

- leader 负责接收命令；
- leader 负责复制日志；
- follower 只负责校验并跟随；
- 通过 `nextIndex[]` / `matchIndex[]` 维护复制进度；
- 通过 `commitIndex` / `lastApplied` 维护提交与执行进度。

整个实现写下来，会发现 Raft 其实一直在围绕一个核心目标服务：

> **让所有节点最终拥有同一份、按相同顺序排列的日志。**

而一旦这件事成立，状态机的一致性也就自然成立了。
